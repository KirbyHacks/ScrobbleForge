# ScrobbleForge

Current version: **v1.1.0**.

A resilient, background-oriented Last.fm scrobbler designed for continuous, unattended execution. Ingests full Spotify playlists, complete albums, single tracks, as well as public YouTube and YouTube Music playlists and tracks without requiring Premium or developer credentials, featuring realistic playback simulation, non-overlapping historical timeline synthesis, and configurable rolling 24-hour rate limiting.

---

## Why ScrobbleForge Instead of Other Scrobblers

Most open-source Last.fm auto-scrobblers share the same limitations:

| Feature / Capability | Other Scrobblers | ScrobbleForge |
|---|---|---|
| **Multi-Provider Support** | ❌ Hardcoded to single service | ✅ Spotify, YouTube, and YouTube Music public sources |
| **Playlists, Albums & Tracks** | ❌ Hardcoded to single static track loops | ✅ Full playlists, complete albums, and single obsession tracks |
| **Free Streaming Accounts** | ❌ Blocked by Web API paywalls | ✅ Zero-credential public resolution (No Premium or API keys needed) |
| **Playback Timeline Synthesis** | ❌ Naive real-time flooding (overlapping timestamps) | ✅ Non-overlapping historical timeline synthesis (generates a sequential, non-overlapping virtual playback timeline) |
| **Rolling 24h Quota Guard** | ❌ None or midnight resets (causes HTTP 429) | ✅ Rolling 24-hour persistent SQLite ledger with auto-pause/resume |
| **Two-Factor Authentication (2FA)** | ❌ Broken with deprecated password hashing | ✅ Permanent session key authorization (`auth_helper.py`) |
| **Production Docker Readiness** | ❌ Blocking `time.sleep()` hangs on `SIGTERM` | ✅ Non-root (`1000:1000`), persistent WAL SQLite, signal-safe |

## Core Technical Mechanisms & System Guarantees

ScrobbleForge replaces subjective claims with explicit, software-controlled mechanisms:

- **Non-overlapping historical timeline synthesis (generates a sequential, non-overlapping virtual playback timeline)**: Generates sequential track start times respecting authentic track runtimes, ensuring no two tracks generated by the engine ever occupy overlapping time slices in the synthesized scrobble history.
- **Rolling 24-hour persistent SQLite ledger with auto-pause/resume**: Records submission timestamps in an ACID-compliant SQLite ledger using an exact 24-hour sliding window, automatically pausing when quotas approach limits and resuming as older entries age out.
- **Configurable daily safety ceiling (default: 2,750/day buffer against Last.fm's ~2,800 limit)**: Enforces an intentional buffer below Last.fm's ~2,800 daily submission ceiling to prevent HTTP 429 rate-limiting.
- **Authentic track duration modeling with Last.fm 30-second submission clamping**: Models true track runtimes from source metadata while strictly clamping minimum scrobble duration to 30 seconds per Last.fm API submission rules.
- **Delivery Semantics**: Scrobble delivery operates under at-least-once semantics during ambiguous network timeouts. If Last.fm accepts a submission but the network response drops, the engine will retry upon reconnect, which may occasionally produce duplicate scrobbles for that track.

## Operating Modes

### 1. `realistic` (Real-Time Playback Emulation)
- Simulates real-time listening behavior.
- Broadcasts `track.updateNowPlaying` to Last.fm immediately so profiles show active playback.
- Submits `track.scrobble` at the 50% / 4-minute mark per official Last.fm rules.
- Adds randomized inter-track pauses (1 to 4 seconds).
- Yields ~300 to 500 scrobbles per day, paced strictly by actual track durations.

### 2. `max_limit` (High-Throughput Virtual Timeline)
Accelerates initial ingestion via historical timeline synthesis while enforcing the configured daily safety ceiling (`MAX_DAILY_SCROBBLES`, default 2,750/day buffer). While this ceiling acts as an upper safety guard against API rate limits, sustained long-term throughput settles around ~400–500 scrobbles/day to respect authentic track playback durations and timeline monotonicity without generating future timestamps.

#### Mathematical Timeline Model
- **Real-Time HTTP Submission Cadence**: In `max_limit` mode, real-time HTTP submissions occur every ~32 seconds (`random.uniform(31.5, 33.0)`).
- **Virtual Historical Buffer Window**: Virtual track timestamps are anchored in the past, initialized from a 3-day buffer window (`now - 3 days` or loaded from persistent state).
- **Full Duration Advancement & Strict Monotonicity**: Virtual track timestamps advance by each track's full duration plus padding (`duration_sec + 2s padding`), with tracks shorter than 30s clamped to 30s:
  ```text
  timestamp[i+1] = timestamp[i] + max(30, duration_sec) + 2s
  ```
  The timeline is strictly monotonically increasing ($\text{timestamp}_{n+1} \ge \text{timestamp}_n + \max(30, \text{duration}_n) + 2\text{s}$). Once the virtual cursor reaches the wall-clock present, it transitions to real-time duration pacing to prevent future timestamps, capping sustained throughput at ~400–500 tracks/day without jumping backwards into the past.
- **Contiguous Virtual History**: By decoupling the physical HTTP submission cadence (~32s) from the virtual playback timeline (`duration_sec + 2s padding`), this produces a contiguous, sequential, non-overlapping listening history on Last.fm without compressing song lengths or generating overlapping playback intervals.
- **Rolling Quota Enforcement**: Records each submission at actual submission time (`now`) in the rolling 24-hour SQLite ledger, automatically throttling when the count reaches `MAX_DAILY_SCROBBLES` until older timestamps age out.

#### Real Throughput Dynamics & Present Convergence
- **Initial High-Throughput Burst**: Because virtual timestamps start in the 3-day buffer window (`now - 3 days`), `max_limit` delivers an initial high-throughput burst submitting tracks every ~32 seconds. Over the first ~13 hours of continuous operation, the engine can submit up to ~1,440 tracks into this historical window without timestamps colliding or breaching the wall-clock present.
- **Convergence to Authentic Playback Rate**: Because virtual time advances ~6.6× faster than wall-clock time (~212s authentic duration vs ~32s submission), the cursor catches up to the wall-clock present (~13 hours in). Once caught up, non-overlapping timeline monotonicity prevents future timestamps by pausing for each track's authentic duration before submitting. The 2,750/day limit remains an upper safety ceiling; the actual sustained rate settles around ~400–500 tracks/day.

### 3. `custom_interval` (Fixed Interval Submission)
- Submits scrobbles at a fixed user-defined interval in seconds (`CUSTOM_INTERVAL_SECONDS`, default 60s).
- Submissions use the current timestamp while continuing to enforce the rolling 24-hour safety ceiling.

## Using .fmbot through Last.fm

ScrobbleForge sends track details to Last.fm. [.fmbot](https://fm.bot/commands/plays/) reads that account to show the artist, song, album and playback status in `.fm` and `/fm`.

1. Link the same Last.fm account in .fmbot.
2. Set `SCROBBLE_MODE=realistic` and `UPDATE_NOW_PLAYING=true` to show "now playing" when each track starts.
3. Run `.fm embedmini` to show a small album cover when one is available. In `/fm`, choose `EmbedMini` under `embed-type`. Use `.mode` to change the default format.

Only `realistic` shows active playback. `max_limit` sends past scrobbles, and `custom_interval` sends them at a fixed interval. Pauses, quota waits and retries do not refresh "now playing". Retrying a scrobble keeps its original start time. Last.fm has no documented way to clear or pause that status, so it may remain visible until it expires. .fmbot may also take a while to show changes. A temporary failure to update the status does not stop scrobbling; an authentication error stops the engine, and a rate limit makes it wait.

Spotify playlist embeds sometimes omit the album. When that happens, ScrobbleForge checks the same track's public page before sending it to Last.fm. The ID, full title and artist must match. Results are kept in memory for later plays. A failed lookup leaves the album empty; rate-limited lookups wait 15 minutes. The first lookup can add a short delay before playback, including for tracks loaded from an old cache.

For YouTube Music, ScrobbleForge reads album links. For single videos and Data API playlist items, it can also read a Topic-channel description generated by YouTube, if the title and artists match. It keeps live, remix, clean, explicit and unreleased labels. Missing albums stay empty; durations, view counts, years and playlist names are not used as album names. Old YouTube caches are refreshed once for these changes.

.fmbot finds covers in its Spotify/Last.fm catalog. A cover can still be missing when the track details are correct. [`track.updateNowPlaying`](https://www.last.fm/api/show/track.updateNowPlaying) accepts album details, but no custom image URL. YouTube video thumbnails are not sent as album art. ScrobbleForge uses the existing .fmbot and does not post Discord messages on its own.

To check a track, compare the artist, full title and album on Last.fm with `.fm embedmini` during playback. After the scrobble is sent, check the recent-track entry too. A missing cover alone does not mean the scrobble failed.

## Quick Start (Docker)

### Option A: Using Pre-Built Image (No Git Clone Required)

1. Create a project folder and generate the starter configuration files:

```bash
# On Linux / macOS:
mkdir -p data && chown -R 1000:1000 data  # Pre-creates data volume for non-root 1000:1000 container user
docker run --rm -v "${PWD}:/out" ghcr.io/kirbyhacks/scrobbleforge:latest init

# On Windows PowerShell:
docker run --rm -v "${PWD}:/out" ghcr.io/kirbyhacks/scrobbleforge:latest init
```

*(Alternatively, download `docker-compose.yml` and `.env.example` directly from GitHub).*

2. Edit `.env` with your Last.fm API Key, API Secret, and music source URL:

```dotenv
LASTFM_API_KEY=your_lastfm_api_key
LASTFM_API_SECRET=your_lastfm_api_secret
MUSIC_SOURCES=https://open.spotify.com/playlist/37i9dQZF1DXcBWIGoYBM5M
```

3. Start the container:

```bash
docker compose up -d
docker compose logs -f
```

4. **One-time browser authorization with persistent session key storage**:
   On first launch, ScrobbleForge displays an authorization link in the container logs:
   ```text
   ======================================================================
   [ACTION REQUIRED] AUTHORIZE LAST.FM IN YOUR BROWSER
   Please open the following link and click "Yes, allow access":

     https://www.last.fm/api/auth/?api_key=...&token=...

   Waiting for browser approval (checking every 6s, 15m timeout)...
   ======================================================================
   ```
   Open the link in your browser and click **"Yes, allow access"**. ScrobbleForge automatically detects your approval, saves the permanent key to `data/session.key`, and immediately begins scrobbling.

Settings can be specified in `.env` or passed directly as Docker environment variables.

| `LASTFM_API_SECRET` | *(required)* | Last.fm Shared Secret |

| `MUSIC_SOURCES` | *(required unless legacy used)* | Comma-separated playlist, album, or track URLs (repeated entries preserved for queue weighting). Generic source variable taking precedence over legacy Spotify variables. Supported providers: Spotify, YouTube, and YouTube Music |
| `SPOTIFY_PLAYLIST_URL` | *(legacy fallback)* | Legacy Spotify playlist, album, or single track URL. Used when `MUSIC_SOURCES` is omitted |

| `SPOTIFY_CLIENT_SECRET` | *(optional)* | Spotify Developer Client Secret |

| `SCROBBLE_MODE` | `realistic` | Pacing mode: `realistic`, `max_limit`, or `custom_interval` |
| `CUSTOM_INTERVAL_SECONDS` | `60` | Delay in seconds when `SCROBBLE_MODE=custom_interval` |
| `MAX_DAILY_SCROBBLES` | `2750` | Configurable daily safety ceiling (buffer against Last.fm's ~2,800 limit) |

| `LOOP` | `true` | Repeats queue infinitely for continuous background scrobbling |
| `UPDATE_NOW_PLAYING` | `true` | Broadcasts "Now Playing" in `realistic` mode |
| `INTER_TRACK_PAUSE_MIN` | `1.0` | Minimum pause between tracks in seconds |
| `INTER_TRACK_PAUSE_MAX` | `4.0` | Maximum pause between tracks in seconds |
| `SOURCES_REFRESH_INTERVAL_HOURS` | `12` | Hours between automatic source refreshes. Takes precedence over `SPOTIFY_REFRESH_INTERVAL_HOURS` |
| `SPOTIFY_REFRESH_INTERVAL_HOURS` | `12` | Legacy hours between automatic Spotify source refreshes |
| `DATA_DIR` | `./data` | Directory where SQLite state and cache are persisted |
| `LOG_LEVEL` | `INFO` | Console logging verbosity (`DEBUG`, `INFO`, `WARNING`, `ERROR`) |

## Supported Source Providers & Reference URLs

ScrobbleForge ingests music metadata through provider-agnostic source clients that normalize upstream payloads into canonical track models:

### 1. Spotify (`spotify`)
- **Supported URL Types**:
  - `https://open.spotify.com/playlist/<id>`
  - `https://open.spotify.com/album/<id>`
  - `https://open.spotify.com/track/<id>`
  - URIs: `spotify:playlist:<id>`, `spotify:album:<id>`, `spotify:track:<id>`
- **Authentication**: Zero credentials required for public embeds. Optional `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET` for developer app access.

### 2. YouTube & YouTube Music (`youtube`)
- **Supported URL Types**:
  - `https://www.youtube.com/playlist?list=<id>`
  - `https://youtube.com/playlist?list=<id>`
  - `https://music.youtube.com/playlist?list=<id>`
  - `https://www.youtube.com/watch?v=<id>`
  - `https://music.youtube.com/watch?v=<id>`
  - `https://youtu.be/<id>`
- **Authentication**: **Zero credentials required** for public playlists and tracks. Queries public YouTube Music endpoints directly using standard HTTP requests (no `yt-dlp` or browser cookies required).
- **Optional API Key**: `YOUTUBE_API_KEY` can be configured to route requests through the official Google Cloud YouTube Data API v3 (`playlistItems.list` and `videos.list`).
- **Metadata Normalization**: Presentation labels such as `(Official Music Video)`, `[Official Audio]`, and `[HD]` are removed. Recording versions, including remasters and extended mixes, are preserved. Topic channel identity takes precedence over hyphens inside song titles.
- **Conservative Omission Policy**:
  - Private, deleted, or region-restricted items are filtered out with logged omissions.
  - Ambiguous videos where music artist cannot be determined with adequate confidence are omitted rather than fabricating metadata.
  - Channels (`/@channel/videos`) and YouTube Shorts (`/shorts/...`) are out of initial scope.
- **Missing Metadata**: The provider preserves unknown album, album artist, track number, and duration as unknown. The legacy playback engine uses a 180-second pacing estimate when duration is missing; this is not a recovered duration. Source ingestion preserves known album artist and track numbers rather than substituting queue positions.
- **Cache Upgrade**: v1.1.0 uses YouTube normalization schema 3. Older YouTube caches are refetched on the next start so incorrect artist/title mappings are not retained. Forced refresh also updates the disk cache.
- **Access Limits**: Public references are supported; access remains subject to upstream availability. The default YouTubei integration uses unofficial endpoints and may need updates when their responses change. Supplying `YOUTUBE_API_KEY` selects Data API v3 rather than an automatic fallback after a YouTubei error.

## Offline and Local Fallback Sources

When no configured source returns tracks and source ingestion has not raised an error, ScrobbleForge looks for fallback files in the working directory or `./data`. Failed configured sources abort startup; a cached Spotify source may still be used after a fetch failure. To use a local list directly, leave music source references empty:

- `tracks.txt`: Line-delimited entries in `Artist - Title` format.
- `tracks.csv`: Exportify or TuneMyMusic CSV exports with standard track headers.
- `tracks.json`: JSON list containing objects with `title`, `artist`, and `duration_ms`.

## Test Suite

ScrobbleForge includes isolated unit and provider contract suites covering metadata, errors, pagination, caches, queue persistence, quota mathematics, and timeline pacing. CI runs both suites before publishing a Docker image:

```bash
# Install test dependencies and run all offline release checks:
python -m pip install -r requirements-dev.txt
python -m pytest tests/unit tests/contracts -q

# Legacy unit-only runner (does not include provider contracts):
python -m unittest discover -s tests/unit

# Or via backward-compatible test runner:
python tests/test_suite.py
```

Live API tests remain opt-in (`RUN_LIVE_TESTS=1`) and are outside the CI release gate.

To build a source archive from the current checkout, including uncommitted source changes:

```bash
python scripts/build_release.py
```

This produces `dist/scrobbleforge-1.1.0-source.zip` and a SHA-256 checksum. The archive includes source, offline tests, the README, license, and Docker/configuration templates. Credentials and local state are excluded.
